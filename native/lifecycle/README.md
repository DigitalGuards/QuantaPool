# Guarded local native pool lifecycle

These executable helpers use the fresh network described in `../network/README.md`. All transactions require literal loopback endpoints, chain ID `3151916`, the exact recorded execution genesis, complete beacon configuration, genesis time, unique fork version `0x31519160`, and current canonical deposit runtime. Every command selects the disposable fixture explicitly. The helpers never load an ambient wallet seed.

Use these environment values only for this identified local fixture:

```sh
export QUANTAPOOL_PUBLIC_LOCAL_NETWORK=3151916
export QUANTAPOOL_PUBLIC_DEV_ACCOUNT=2
export QUANTAPOOL_PUBLIC_DEV_CHAIN_ID=3151916
```

The transaction actor and bootstrapper are public fixture account 2, the immutable fee beneficiary is account 1, and depositors are accounts 0 and 3. Actual addresses and receipts are recorded in ignored `findings/native-network-20260915/lifecycle/pool.json`. A separate random validator key stays in the ignored, permission-restricted `controlled-key/` directory. Its public deposit messages and signed exit are separate artifacts.

Build the small application helpers with `bash native/lifecycle/build-helpers.sh "$SOURCE_ROOT"`, where the two pristine source subdirectories match `../network/source-lock.json`. The script checks both source pins and clean worktrees before and after building, uses Go 1.26.5, and records output hashes. The finality analyzer uses the current pinned `native/proofs` module with the same explicit `develop` layout as the proof tests.

`transactions.js` signs bounded native type-2 transactions, saves each exact signed message before broadcast, and polls raw RPC receipts. Named retries reuse the same hash and nonce. Receipt confirmation checks canonical execution block hashes. The transaction lock prevents two local helpers from accidentally sharing an actor nonce; on-chain mechanical functions remain permissionless. Contract ABI and bytecode files are frozen with source hashes and compiler provenance for each live graph. Native address prediction uses pinned go-qrl `crypto.CreateAddress`.

The lifecycle sequence is:

1. Build the current pinned helpers, prepare a fresh validator using `prepare-key.py`, capture a fresh bootstrap checkpoint, and deploy the finality, portfolio, gate and pool graph with `node native/lifecycle/run.js deploy WITNESS`. Bootstrap selection remains an explicit trust assumption. A bootstrap-only artifact proves no new finality certificate.
2. Bind the validator's public deposit messages to the actual pool using `prepare-key.py --bind-pool`. `run.js bootstrap` sends exactly 2,000 QRL of operator preparation capital through the immutable gate to the canonical deposit contract. `run.js deposit-users` sends 20,000 and 22,000 QRL into refundable pending deposits. User funds remain in the pool during bootstrap registration.
3. Run `keeper.py --watch-seconds 14400`, `start-validator.py`, `observe.py --watch-seconds 7200`, and `prepare-exit.py --wait-seconds 5400`. The keeper verifies captured native signatures and submits 86 authenticated committee positions per accepted update. The other helpers observe registration and export a public exit once a canonical index exists. The signer exports the message without broadcasting it.
4. Submit a complete authenticated portfolio checkpoint and finish ledger staging. `checkpoint.js` handles the native account proof, complete parent-linked beacon history, ordered validator proofs and ledger batches. For admission, also export the bootstrap candidate's native validator witness at that exact checkpoint. Hold the keeper's root steady during this bounded sequence using `keeper.pause`; wait for `keeper/paused.json`, then use the transaction lock. Remove the pause marker promptly after the sequence.
5. `run.js admit STATE_WITNESS` requires the original public epoch-zero exit to have been available before pooled funding, checks candidate identity and the already settled root, and calls the gate's atomic admission. The contract verifies the canonical 2,000 QRL balance and pool recipient, verifies and stores the exit, adopts the bootstrapper's 2,000 QRL as their own stake, and funds the remaining 38,000 QRL. The driver checks exact cash and principal changes. The 42,000 QRL user deposits leave 4,000 QRL cash after funding, with 44,000 QRL total economic capital.
6. The top-up follows the unmodified execution-follow and voting rules. Maintain finality and complete portfolio checkpoints before and after beacon consumption so pending native deposits remain accounted for. The validator must then activate and satisfy the native 16-active-epoch exit rule. `run.js request-all` queues full user positions in deterministic order and requests the next gate exit. An independent relay uses the stored public message and records native acceptance, exact block inclusion and finalized state separately.
7. After actual native withdrawals and a complete finalized terminal portfolio, finish ledger staging and run `run.js claim-all`. The driver checks each user's reserved principal and reward claims, the fee reserve, and all native payouts. It separately reconciles incidental fixture proposer tips, native withdrawal credits and transaction gas. Principal shortfall is recorded if present. Fees are taken only from the contract's already-earned fee reserve, and any remaining cash must stay explicitly accounted for.

After claims complete, `node native/lifecycle/report.js` performs a read-only final crosscheck. It pins the frozen creation artifacts to their actual deployments, rechecks canonical deposit and withdrawal tuples, compares all observed validator returns with the complete contract-authenticated withdrawal total, and reconciles contributions plus net validator returns against payouts and remaining cash. It writes ignored `completed-lifecycle.json`, with user payouts separated from incidental proposer tips and transaction gas. The gas report includes mined reverts. This report identifies the original frozen graph explicitly, so later source hardening and any separate recovery experiment retain their own evidence.

For this recorded run, `python3 native/lifecycle/finish.py --watch-seconds 900` performs the final sequence automatically after terminal accounting is ready. It requires the ignored helper PID/argument manifests, waits for the finalized-zero observation and complete FIFO reservation, pauses the keeper, executes claims and the report, and then stops only processes whose current arguments exactly match their recorded lifecycle identities. Cleanup requires a complete zero-cash drain. The fresh enclave, execution/beacon clients and genesis validators continue running. A completed cleanup record makes repeated invocation read-only.

Fresh deployment now passes the immutable validator operator explicitly and verifies its getter. The original funded graph predates that admission guard and the later pool-checkpoint recovery deadline and capacity hardening. Its original ABI and creation artifacts remain frozen throughout the lifecycle; its normal-flow evidence does not establish those later protections.

`run.js status` is read-only. `keeper.py --until-fresh --watch-seconds 300` performs a bounded catch-up and returns only with at least 32 slots of economic freshness margin. Keep a single background keeper per graph. A pause is local coordination, carries no on-chain authority, and does not extend freshness or the immutable recovery deadline.

After the first settled checkpoint and validator admission, run `python3 native/lifecycle/maintain-checkpoints.py --watch-seconds 7200 --interval-slots 64`. It holds the finality keeper briefly at a fresh root, submits a complete portfolio checkpoint and resumes finality in a `finally` block. The execution cutoff must follow registry changes. This keeps normal proof intervals small while native deposit voting and validator eligibility advance. A second ordinary checkpoint can prove that cash plus the canonical 2,000 QRL validator balance plus the unconsumed 38,000 QRL top-up still equals the 44,000 QRL stake ledger.

The optional `NativeCheckpointExecutor` reduces transaction overhead for complete histories. Deploy its separately qualified artifact with `node native/lifecycle/deploy-executor.js`; its manifest and frozen artifact live alongside the original four contracts without replacing them. It has immutable pool and portfolio destinations, typed permissionless calls, at most three four-block groups per transaction, and no funds or accounting authority. The last call can finalize the portfolio and complete ledger staging atomically. Current local batches use a measured 6-million gas cap to fit efficiently within the chain's actual 20-million block gas limit. Calldata and signed transaction size are checked independently.

The initial local backlog exposed the freshness budget twice: ordinary proof submission reached finalized-state age 66 before its final commit, and a later batched attempt also crossed the 64-slot limit. Both attempts reverted without admitting pending deposits. Immutable compact-proof caching, renewed native root/branch verification, bounded signing concurrency and the measured transaction gas cap allowed the complete 1,184-block initial history to settle at age 62. Canonical validator admission then succeeded at age 64. These results show why commissioning and periodic maintenance need explicit time and gas budgets; freshness was preserved throughout.

All commands must be run from the QuantaPool cell unless their path is resolved explicitly. Helpers, source revisions, runtime manifests, native proof artifacts and transaction receipts distinguish actual protocol execution from reference models and VM tests. RPC observations in `consensus-cash-events.jsonl` and `lifecycle-observation.json` are operational evidence; contract-authenticated roots and complete proofs establish economic checkpoints.

The 3-second local clock does not reduce epoch counts or execution-follow requirements. Deposits can require more than one 512-slot voting period before they are consumed. An index-bound exit is obtained after operator-funded registration and before pooled top-up. This fixture configures execution tips to the operator, while the native protocol continues to permit the signer to choose that recipient. Transaction-fee routing remains an unresolved product guarantee and is excluded from any claim that those tips are enforced pool rewards.
