# Native portfolio proof qualification

`npm run test:proofs` builds the current compiler-qualified candidate, exports fresh public fixtures with unchanged Qrysm, and executes portfolio, funding-gate and complete pool-adapter plans in unchanged go-qrl QRVM. All three plans use an explicit synthetic finality authority. The isolated gate plan uses a pool release fixture; the adapter plan executes the real NativeQrlPool and its ledger. The gate tests use a fresh discarded signing key, genuine deposit and exit signatures, and the exact canonical native deposit runtime. They test an actual 2,000 QRL deposit followed by an atomic 38,000 QRL top-up. The adapter plan verifies matched accounting before and after beacon consumption, plus fee exemption for external validator deposits and an explicitly artificial unrelated native cash credit. No transaction is broadcast by this test command.

The gate constructor binds both the canonical 64-byte `0x42` address and the pinned runtime. The VM fixture executes the canonical deposit constructor at an ordinary generated address, then uses its actual native code, nonce and completed 64-byte storage values for an explicitly synthetic `fixture-predeploy` allocation at the canonical address. It copies no QRL balance and modifies no network genesis. Keeping the ordinary copy also proves that the identical runtime at a different address is rejected. Storage comes from native QRVM execution, without assumed Ethereum slot layouts.

The current candidate also restricts preparation to the immutable validator operator and enforces 64 lifetime validator admissions. Capacity tests perform 64 actual portfolio registration calls using canonical native-SSZ witnesses and reject the 65th, including after one registered validator becomes terminal. Their gate caller and finality authority are explicit fixtures. A separate real-gate test uses a clearly synthetic full-registry interface and verifies that new operator preparation is rejected without moving QRL. Existing tests retain permissionless completion of valid operator preparation.

Five additional plans execute the real pool's independent accounting timeout: no first settlement; successful renewal exactly at the deadline; newer complete portfolio work without pool application; expiry during ledger staging; and preservation of pending refunds, reserved user claims, earned fees and late recovery cash. Fixture finality remains healthy in these tests. The current gate rejects preparation after pool timeout, and expired pool settlement cannot revive normal operation. These are VM regressions with explicit synthetic native state and timing; actual network timeout evidence is recorded separately.

The Go module pins Qrysm `3b816311ac3e86b7a7af40a062ae290318554f7a` and go-qrl `9b404c38a63bfebe07cfd07b5f5d144d1c2cf9b9`. The contract compiler pin and binary hash come from `config/hyperion-toolchain.json`; the runner enforces them before compiling. Generated fixtures, plans and reports are under ignored `findings/native-proof-tests/`.

The portfolio binds the immutable finality verifier, pool and validator gate. The gate is its only registration caller. Admission requires a full canonical public key, pool withdrawal recipient, exact 2,000 QRL balance and effective balance, and an unslashed validator without activation or exit. The gate records the original bootstrap payer, publishes an epoch-zero signed exit, and forwards exactly 38,000 QRL from the pool to the pinned deposit contract. Failed proof, signature, pool release or native deposit execution reverts the entire admission. The pool chooses when its liquidity and withdrawal queue permit funding.

A checkpoint proves pool cash and all registered validator balances against one accepted finalized state. State generalized indices are 898 for execution state root, 902 for execution block and 42 for consumed execution deposits. Validator and balance branches have 46 and 44 siblings and agree on the canonical list length. Account proofs use the native 64-byte address hashed with Keccak256 and canonical native account RLP.

Every occupied beacon header from the new finalized header back to the prior accepted header is supplied in reverse parent order. Empty slots require no fabricated block. Each block proves its complete ordered withdrawal list at body generalized index 414 and complete ordered deposit list at index 22. Deposits to registered keys after admission are counted even when a third party sent them. Native withdrawals count only for registered indices and the pool recipient. This separates native consensus changes from execution tips, unrelated cash and external validator top-ups. The original 2,000 QRL at each admission is an explicit principal baseline. The gate's binary-search funding history counts only pool top-ups already sent at the execution cutoff and still unconsumed by its paired beacon deposit cursor.

Work is bounded to four validators or four blocks per call. Registry ordering and header ancestry enforce complete coverage. A snapshot commits exactly once after all coverage succeeds; staged validator results remain hidden. Anyone can progress mechanical work or discard stale work. The finality verifier's economic freshness applies throughout staging. An accepted terminal-zero record observes actual zero at that slot. Subsequent deposits can create another balance.

The public exit is available as soon as pooled funding succeeds. Anyone can relay it when native eligibility permits. Public availability also permits early validator churn after eligibility; the queue's requested-exit order is an operational signal, since the public signature remains independently usable. Validator proposers still control execution-tip routing. This implementation does not authenticate a promise that such tips are routed to the pool.

The bootstrap payer bears the preparation risk before pool admission. Its 2,000 QRL already resides in native staking while canonical registration and public exit authorization are obtained. If activation funding never follows or the signer disappears before publishing its exit, unchanged protocol rules can leave that preparation capital unavailable. Ordinary pool depositors fund the top-up only after all admission conditions succeed atomically.

Read-only local capture commands are deliberately separate from component tests:

```sh
python3 native/proofs/capture-finality.py --network "$NETWORK" --output-dir "$CAPTURE" --bootstrap-slot "$BOOTSTRAP" --attested-slots "$ATTESTED" --allow-unfinalized-updates
(cd native/proofs && GOWORK=off go run ./cmd/analyze-finality --capture-dir "$CAPTURE" --output "$CAPTURE/witness.json")
python3 native/proofs/capture-checkpoint.py --network "$NETWORK" --account "$POOL" --slot "$FINALIZED_SLOT" --output-dir "$CASH_CAPTURE"
(cd native/proofs && GOWORK=off go run ./cmd/verify-cash --capture-dir "$CASH_CAPTURE" --output "$CASH_CAPTURE/witness.json")
python3 native/proofs/capture-flow.py --network "$NETWORK" --start-root "$FINALIZED_HEADER_ROOT" --stop-root "$PRIOR_HEADER_ROOT" --output-dir "$FLOW_CAPTURE"
(cd native/proofs && GOWORK=off go run ./cmd/export-flow --capture-dir "$FLOW_CAPTURE" --output "$FLOW_CAPTURE/witness.json")
```

Use absolute values for the capture-directory variables when entering the module subdirectory. These readers accept only the identified loopback fixture and verify exact genesis/configuration identities. `cmd/export-state` additionally exports a selected complete registry from public state SSZ, checking its native root against the supplied finalized header. RPC capture establishes input provenance; the deployed finality verifier and proof consumers establish on-chain authority. Historical state availability, archival capture and enough keeper throughput to finish within the freshness window remain operational requirements.

The optional mechanical executor and reproducible atomic settlement tests are described in `CHECKPOINT-EXECUTION.md`. `SCALE.md` records measured costs, capacity projections and remaining launch conditions.

Current-pin public exit tooling lives in `cmd/relay-exit` and `observe-exit.py`. The relay accepts no signing key. It requires the exact local genesis root/time, chain, fork and independently pinned validator public-key hash. `-verify-only` checks the public native signature without broadcasting; `-submit-local-exit` submits the same message when requested and eligible. HTTP acceptance, block inclusion and finalized state are distinct observations. The observer additionally runs the full local execution/beacon manifest guard and labels its output as RPC evidence. A complete portfolio proves the corresponding finalized economic state on-chain.

The actual local validator 64 demonstrated the full public-exit bootstrap sequence. Its 2,000 QRL preparation became canonical in block 1792. The signer exported an epoch-zero public exit at head 1799, before the pool's authenticated 38,000 QRL funding transaction at execution slot 1888. The gate stored the same signature atomically with funding. Native activation later became epoch 360; the unmodified 16-active-epoch rule made epoch 376 the first eligible exit epoch.

After user FIFO requests and the gate's exit request at execution slot 2939, an independent relay rechecked the on-chain signature, canonical request receipt, native public-key identity and signature domain. It submitted the unchanged public message once at head 3009 in epoch 376. Qrysm returned HTTP 200, block 3010 included the exact signed message, and a fixed finalized-state observation at slot 3016 recorded exit epoch 381 and withdrawable epoch 397. The relay accessed neither a validator signing key nor an execution signing key. These acceptance, inclusion and finalized RPC observations are preserved separately from contract-verified portfolio evidence. Withdrawal epoch eligibility alone does not establish returned principal; actual native withdrawals and their matched checkpoint must still reconcile.
